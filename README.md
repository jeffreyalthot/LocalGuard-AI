# LocalGuard V1.1 experimental
Windows 10/11, C++17, MinGW/Ninja. Run build.cmd then build\LocalGuard.exe. Administrator enables ETW; use only trusted source/build directories, preferably on a test machine. Observation only, no firewall changes or external transmission. Data directory is build/data beside executable, independent of launch directory. Do not run concurrent copies. Separate persistent aggregate profiles for ETW and polling; no migration of old profile. Per-executable-name TCP baseline is in-memory only, capped at 2048 names; names are not verified identities. Registry Run/RunOnce checks current user and native machine view every ~60 seconds; changes are not necessarily malicious. SHA-256 watch.txt baseline in memory only; create build/data/watch.txt before launch. CPU percentage normalized by logical processors, working set in KiB, sampled roughly every minute. New alerts are advisory and not fused into aggregate risk. No service, neural network, active blocking, protected storage or tamper resistance. Windows modules require real Windows testing; portable detector and behavior tests can run on Linux. Build script adjusts future timestamps only in project root. Stop with Ctrl+C. Do not use as replacement for Defender.

## V2.0 experimental
Adds bounded four-cycle risk correlation, combines behavioral, registry and file signals with global risk, and recommends manual review. No automatic blocking or service installation. File and registry flags are held until the next 60-second check; repeated flags are not independent evidence. The score is heuristic, not a probability. Global detector still learns independently. Run build.cmd then run.cmd. Use a trusted directory, do not elevate untrusted binaries. Windows Defender and firewall should remain enabled. Windows full build and runtime, long-duration performance and detection efficacy remain unverified. This is source code, not a certified deployment package.

## V2.1 - synthetic validation

File and registry flags are evaluated on their actual sampling cycle. SimulationTest uses synthetic snapshots and injected file/registry flags, not real attacks or sensor integration tests. 1000 deterministic trials across seven incident categories and one normal category. Results do not estimate real-world detection or false positive rates. No active blocking. Windows build and live sensor tests remain required. Keep Defender and firewall enabled.

## V3.0 — Decision and campaign
Decision.cpp is integrated into the Windows loop. It recommends review, urgent review, or restoration of sensor visibility; it does not block or quarantine. Campaign.exe runs 100 million deterministic synthetic signal records (not distinct attacks; observable combinations repeat). Its oracle checks the signal contract, not malware ground truth. See CAMPAIGN.txt and TESTS.txt for actual Linux portable results. Windows build and live sensor validation remain outstanding. Keep Defender and firewall enabled. Run build.cmd then build\Campaign.exe for full campaign, then run.cmd for monitoring. No production readiness claim.

## V4.0 — experimental adaptive coordinator
Adds a bounded 12-cycle evidence history, cross-signal scoring, 2–5 second sampling and a 12-clean-cycle learning cooldown. Independent file and registry signals remain visible when snapshot telemetry fails. Global and per-name learning are gated by previous-cycle evidence and current file/registry alerts; this is not complete poisoning resistance. No attribution of AI-generated attacks, automatic blocking, malware scanner or perfect coverage. Keep Defender enabled. Existing sensors retain their limitations. ## V5.0 DataDefense
Adds bounded destination-set tracking (16384 connections maximum), adaptive novelty baseline and 12-cycle correlation of destination churn, integrity, persistence and behavioral signals. Urgent correlation accelerates polling and freezes learning on subsequent cycles. Destination counts are not byte counts; no proof of exfiltration or AI attribution. No automatic blocking. No packet content collection. Portable tests include 10000 synthetic sequences, not independent attacks. Windows integration and performance remain untested. Keep Defender and firewall enabled. Run build.cmd then run.cmd.

## V6.0 — active defense with explicit approval
The monitor remains observation-only; Protection.h adds a containment recommendation when a network burst and a persistence or integrity change coincide with valid telemetry and a score >=60. This is not proof of common attribution. `contain.cmd` (administrator) asks for one executable path and explicit BLOCK confirmation, then creates a named outbound Windows Firewall block rule. `release.cmd` removes only that named rule. Do not block critical programs or shared hosts. `harden.cmd` asks approval to enable all firewall profiles and Defender PUA protection; changes may be partial if a command fails. These scripts require Windows PowerShell and have not been executed in this Linux environment. No automatic blocking, quarantine, kernel protection or guarantee against exfiltration. Review executable identity and protect the installation directory before elevation. Keep Defender and security updates active. TESTS.txt records portable tests only.

## V7.0 resilience
Create build/data/watch.txt before starting the monitor (a harmless text file). Run from a trusted directory, with administrator privileges for ETW. Learning is deliberately paused if ETW, the witness file, registry, telemetry or journal is unavailable; polling still observes. A journal failure latches until restart. Twelve healthy quiet cycles are required by the resilience gate; other adaptive gates may extend this. A cycle over 500 ms prevents the new scheduler from accelerating. This is not a CPU quota. The existing manual containment and hardening scripts are unchanged. No automatic firewall action, service, or kernel protection is added. Windows integration is untested; portable tests only. The witness file is not comprehensive file protection.

## V8.0 — extension active (les instructions ci-dessous priment sur les anciennes)
- `run.cmd` : observation seule. `run-active.cmd` : consentement explicite pour demander un scan rapide Microsoft Defender après trois cycles urgents consécutifs avec capteurs sains. Un seul processus de commande à la fois, délai de 900 cycles entre demandes (environ 30–75 minutes hors traitement). Le délai est en mémoire et repart au redémarrage. Le scan peut consommer beaucoup de CPU et Defender peut appliquer sa propre politique de quarantaine. Un code de retour réussi ne prouve pas l'absence de malware.
- `audit.cmd` : lecture de l'état Defender et du pare-feu. `protect-folders.cmd` : mode audit de l'accès contrôlé aux dossiers, uniquement si désactivé; ne bloque pas les écritures. Ne désactive pas une protection déjà active.

- Correction : une énumération de processus interrompue est signalée comme télémétrie incomplète.
- Créer le témoin uniquement s'il est absent : `if not exist build\data mkdir build\data` puis `if not exist build\data\watch.txt echo LocalGuard baseline>build\data\watch.txt`.
- Tests : 10 tests portables réussis sous Linux. Modules Windows et scripts non exécutés ici. Pas de garantie de détection universelle, de récupération automatique, ni de performances Dual Core mesurées. Sauvegardes hors ligne et OS maintenu indispensables. Windows 10 22H2 nécessite une couverture de mises à jour prolongée ou une migration vers un OS pris en charge.

## V9.0 - Incident retention
The in-memory incident latch holds learning for 30 healthy cycles after evidence, and does not expire while telemetry is degraded. It is not persistent across restarts. IncidentTest checks 1,048,576 transitions and expiry behavior. backup.cmd opens Windows File History for manual backup configuration. No automatic file deletion, firewall isolation or restoration is added. Windows integration remains untested here. The existing opt-in Defender scan policy is unchanged. No guarantee of protection against all attacks.

## V1.0.0 (successor to V9.0)
IncidentStore persists the remaining healthy-cycle hold in data/incident.dat. Missing or malformed state starts with a 30-cycle hold; write failures freeze learning. This is not authenticated storage and cannot resist an administrator or a malicious user with write access. Atomic rename is not a guarantee of power-loss durability. security-events.cmd provides a manual read-only audit of recent failed logons, account/group changes, cleared logs and Defender events; it is not a live sensor. Event text may contain private account information. Existing active scan and confirmed containment policies are unchanged. No Windows integration or resource benchmark was performed here.

## V1.2.2 — Advanced Network Intelligence
NetworkIntel.cpp/.h attributes distinct established TCP remote addresses to snapshot PID and executable name. Alerts at 40 distinct peers or 12 new peers since the previous valid snapshot for the same PID/name. Duplicate addresses are deduplicated. Invalid, oversized or unattributable snapshots reset comparison and freeze learning. Findings feed the existing behavior signal; no automatic firewall rule is created. Limits: 16384 connections, 8192 process identities for this module. PID reuse with identical name, snapshot races, short-lived connections, UDP remote traffic and actual byte volumes are not resolved. Thresholds are heuristic and may flag legitimate applications. Windows integration not compiled here. Linux Release: 16/16 CTest tests passed, including nine network checks. CPU/RAM not measured.

## V1.2.4 — RansomGuard
Optional nonrecursive monitoring of one directory via LOCALGUARD_WATCH_DIR (absolute path, no quotes in value). Run watch-folder.cmd for observation, or set the variable in CMD before run-active.cmd for opt-in Defender quick scans. No files are changed by the sensor. Six-cycle rolling counts: 300 add/modify, 60 rename, 100 delete, or 80 add/modify plus 20 rename/delete. Notifications are not unique files or proof of encryption; no PID attribution. Overflow or sensor failure freezes learning; restart if monitoring cannot recover. Unconfigured monitoring is explicitly logged and does not freeze existing learning. 32 KiB notification buffer, no new permanent thread. Windows integration not compiled or tested here. Test with a disposable folder, not production data. Existing Defender scans can increase CPU load. No automatic file deletion, process termination, or recovery. Portable tests: 18/18, including 7293 threshold combinations plus rolling-window checks.

IdentityGuard distinguishes failed logons (4625), account/group changes and lockouts (4720,4722,4724,4726,4732,4733,4740), and audit changes (1102,4719). ## V1.2.6 — Self-protection
After a trusted build, run `provision-integrity.cmd` once, explicitly approving the new SHA-256 baseline. It refuses to overwrite an existing baseline. Run `run.cmd` first. The executable on disk and its expected digest are checked at startup and every 12 cycles. Missing, unreadable or changed baseline or executable latches an integrity failure until restart; monitoring continues, learning, profile/incident writes and new automatic Defender scan requests are disabled. Existing scans are not cancelled. The check uses a 16 KiB streaming buffer and a 64 MiB file limit. No new thread. The manifest is plaintext, not a signature or independent trust anchor; protect the installation directory with Windows ACLs. An attacker able to replace both executable and manifest before startup can bypass it. No memory integrity, process termination prevention, service or kernel protection. Windows integration and script not tested here. Portable test checks sticky policy only. Do not rebaseline a suspicious executable; preserve evidence and rebuild from trusted sources in a clean directory.

## V1.2.7 — Windows service (experimental)
Build using build.cmd. From elevated Windows PowerShell, after reviewing the binary and scripts, run `./install-service.ps1`. The installer copies the binary to Program Files, creates a separate data directory and configures LocalService. It leaves startup manual. Start with `Start-Service LocalGuard`, inspect `Get-Service LocalGuard` and the installed data/guard.log. After validation, enable boot startup with `Set-Service LocalGuard -StartupType Automatic`. Stop with `Stop-Service LocalGuard`; remove with `./remove-service.ps1`. Files are retained. No automatic restart policy is configured. Service mode is observation only; HKCU refers to the service account, Security log/ETW access may be denied, and the folder monitor is not configured by the interactive environment. Do not run console and service concurrently. SCM running status does not certify sensor readiness. Windows service integration and installer have not been compiled or executed here. Portable regression tests only. If the installer fails, inspect the service and destination manually before retrying. MinGW runtime DLLs may be needed; validate on the target machine.

## V1.2.8 — verified recovery (experimental)
RecoveryCopy is a separate, manually invoked C++17 tool. It copies one regular file at a time (up to 8 GiB), using 64 KiB streaming buffers and SHA-256 (BCrypt on Windows, OpenSSL on Linux). Linux builds now require OpenSSL development headers. Use trusted, private local directories, with an existing destination parent and a new destination directory. Do not run as administrator. Close applications writing the source. The tool rejects observed symlinks/reparse points, checks free space and source size/time, re-reads the copy and publishes payload.bin only after verification. Failed operations can leave payload.partial; never use it. It does not preserve original filename, ACLs, alternate streams or timestamps. No atomic filesystem snapshot, protection against concurrent hostile path changes, guaranteed crash durability or malware scan. Store the printed SHA256 separately on trusted offline media; a digest created after compromise is not evidence of a clean backup. Disconnect backup media after use. Restore to a fresh directory, scan and inspect before manually moving data. Never use on live system files or untrusted shared directories.

Examples (CMD, from project directory, replace paths and digest):
```
build\RecoveryCopy.exe backup "D:\Test\document.txt" "E:\Backup001"
build\RecoveryCopy.exe verify "E:\Backup001\payload.bin" SHA256_FROM_TRUSTED_RECORD
build\RecoveryCopy.exe restore "E:\Backup001\payload.bin" "D:\Restore001" SHA256_FROM_TRUSTED_RECORD
```
Use lowercase 64-digit hexadecimal digest. Destination parent must already exist. No automatic recovery or service integration. Existing service remains experimental and observation-only. Linux portable tests include real file copying and known SHA-256 vectors; Windows BCrypt and service remain untested. This is not a replacement for versioned offline backups or Windows File History.

## V1.2.9 — CyclePolicy
Adds a fixed-memory policy combining eight health inputs, urgency and elapsed processing time. Over 500 ms triggers a three-cycle overload counter; learning requires 12 consecutive healthy, quiet, non-overloaded cycles. New automatic scans are inhibited during overload or degraded health. Existing scan processes are not interrupted. Main uses the policy in addition to existing learning gates. A missing optional folder monitor is not treated as a failed sensor. The timing sample precedes final logging and learning, so it is not a hard CPU or latency limit. All test targets retain assertions in Release; CTest timeout is 120 seconds per test. Linux Release validation: 22 tests, 2048 policy combinations and 1 million synthetic steady cycles. Windows service and native integration remain untested. No measured false-positive improvement or CPU/RAM guarantee. Re-provision executable digest only after verifying the new build, in a fresh installation directory.

## V1.3.0 — Unified Autonomous Cyber Defense (experimental)
UnifiedPolicy centralizes final learning, profile persistence, scan eligibility and polling interval. Evidence and urgency are separate; degraded sensor or state trust forces five-second polling and prevents learning and new scans. All three learning engines share the final gate. Dirty profiles are saved only during permitted cycles or a clean shutdown; unsaved learning may be lost on degradation or ETW fallback. Incident persistence remains independent to preserve evidence. Scan requests still require Recovery cooldown and explicit console opt-in; service remains observation-only. No new thread. UnifiedPolicyTest checks 65,536 input combinations over 12 cycles plus overload transitions. These are synthetic policy tests, not real attacks. Windows main/service and performance remain unverified. Use a fresh trusted build directory and provision-integrity.cmd after compilation; do not overwrite existing trusted baselines blindly. Historical sections above describe older versions.

## V1.3.1 — Threat Memory
Adds a fixed 64-entry in-memory history of rising edges across six evidence categories (network, files, identity, registry, integrity, statistical anomaly). Entries expire after 600 monotonic seconds. At least three distinct categories across two episodes trigger manual review and hold learning through the unified policy and incident engine. Unhealthy samples do not add entries. No automatic scan is triggered solely by this correlation. History is lost on restart; the existing incident hold is persisted separately. Global correlation is not process attribution, and legitimate activity may trigger it. Saturation evicts oldest entries. No new thread or external dependency. Windows integration is not tested here.
